# Миграция Zabbix 4.4 → 7.2

Скрипт `zbx_migrate.py` переносит конфигурацию из Zabbix 4.4 в уже работающий Zabbix 7.2 через API. История и тренды не переносятся.

**Что переносится:**
- шаблоны (с зависимостями);
- узлы с привязанными шаблонами;
- правила сетевого обнаружения;
- действия;
- только те способы оповещения, которые используются в действиях.

**Что уже есть в 7.2, не перезаписывается.** Объект с таким же именем пропускается. Способ оповещения с таким же именем подключается к действиям как есть.

## Почему через API, а не через базу

- Схемы БД 4.4 и 7.2 сильно различаются:
  - applications стали тегами;
  - value maps переехали в шаблоны;
  - изменился синтаксис выражений триггеров;
  - удалённые команды стали глобальными скриптами.
- В 7.2 уже есть данные, поэтому при слиянии таблиц ID будут пересекаться.
- Импорт через `configuration.import` в 7.2 сам прогоняет официальные конвертеры старых форматов.

## Требования

- Python 3.8+ и пакет `requests` (`pip install requests`).
- Пользователь API в 4.4 с типом «Супер-администратор Zabbix».
- API-токен пользователя с типом «Супер-администратор» в 7.2.

## Порядок работы

```bash
cp config.example.json config.json   # заполнить адреса, логин 4.4, токен 7.2, template_map и т.д.

# Этап 1: сравнение и подготовка пакета. В 7.2 ничего не меняется.
python3 zbx_migrate.py prepare -c config.json -p package

# Просмотрите package/*.csv и package/problems.csv.
# При необходимости поправьте флаги "import"/"apply" в package/manifest.json.

# Этап 2: импорт в 7.2.
python3 zbx_migrate.py apply -c config.json -p package --dry-run   # что будет сделано
python3 zbx_migrate.py apply -c config.json -p package
python3 zbx_migrate.py apply -c config.json -p package --steps hostgroups,drules,actions   # выборочно
```

Перед каждым этапом скрипт показывает рекомендации отдельно для старого (4.4) и нового (7.2) сервера. Каждый блок нужно подтвердить ответом «да». Ключ `--yes` отключает вопросы для автоматического запуска.

Повторный `apply` безопасен: уже созданное пропускается. Код возврата 1 означает, что при импорте были ошибки.

## Что сравнивается

| Объект | Как |
|---|---|
| Шаблоны | По имени. Старые шаблоны заменяются на шаблоны 7.2 через `template_map`. Переносятся и шаблоны, которые нужны только действиям. |
| Узлы | По имени, а если не найден — по IP/DNS (тот же узел под другим именем). У существующих узлов показывается, каких шаблонов и групп не хватает; с `sync_existing_hosts` они дописываются. Узлы, у которых видимое имя занято в 7.2, не импортируются. |
| Правила обнаружения | По имени и по диапазону IP, чтобы одну сеть не сканировали два правила. |
| Способы оповещения | Если такой есть в 7.2 (по имени или через `media_type_map`), он подключается, а не создаётся заново. |
| Действия | Ищется дубль с теми же условиями под другим именем и действия 7.2 на те же группы, узлы и шаблоны. Все ссылки сопоставляются по именам. |

**Если условие действия не удалось сопоставить, действие не переносится целиком.** Если просто выкинуть такое условие, действие начнёт срабатывать шире, чем задумано.

## Что не перенесено и что сделать

По каждому объекту, который не перенесён, скрипт выводит **причину** и **что сделать**. Это касается и ошибок, которые вернул сам Zabbix 7.2: конфликт ключей элементов, занятое имя, нехватка прав, лимиты PHP, таймауты и т.п.

| Файл | Содержимое |
|---|---|
| `package/problems.csv` | итог prepare: всё, что не перенесётся, и предупреждения |
| `package/apply_problems_<время>.csv` | итог apply, включая то, что отсеялось при prepare |
| `package/apply_<время>.csv` | результат по каждому объекту |
| `package/{templates,hosts,drules,mediatypes,actions}.csv` | таблицы сравнения с колонкой «что сделать» |

## Параметры по умолчанию

- `actions_status: "disabled"` и `drules_status: "disabled"`: новые действия и правила обнаружения создаются **выключенными**. Так не будет двойных оповещений и двойного обнаружения, пока работает 4.4. Чтобы перенести статус из 4.4, поставьте `"keep"`.
- `sync_existing_hosts: false`: существующие в 7.2 узлы не изменяются, расхождения только показываются.
- `skip_duplicate_actions: true`: действие-дубль не создаётся.
- `skip_drules_same_range: true`: правило с тем же диапазоном IP не создаётся. Действия подключаются к правилу 7.2.
- `create_missing_groups: true`: группы узлов, которые нужны действиям, создаются пустыми.

Остальные параметры описаны в `config.example.json`: фильтры `host_groups`, `hosts`, `actions` и `drules`, а также `proxy_map`, `drop_missing_proxy`, `hosts_disabled`, `include_user_media`, `migrate_all_templates`, `extra_templates`.

## Важно

- **В каталоге пакета открытым текстом лежат пароли** SMTP, SSH и SNMPv3. Он исключён из git через `.gitignore`, не публикуйте его.
- Пользователи не переносятся. Заведите в 7.2 пользователей и группы пользователей с теми же именами и добавьте им медиа, иначе получатели в действиях будут пропущены.
- Прокси 4.4 с сервером 7.2 не работают, нужны прокси версии 7.2 с теми же именами (или `proxy_map`).
- Для удалённых команд на агентах в 7.x нужен `AllowKey=system.run[*]`.
- Перед `apply` сделайте резервную копию БД 7.2: это единственный надёжный откат.
